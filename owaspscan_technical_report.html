Executive Summary

owaspscan is an ultra-lightweight, zero-external-dependency security CLI designed to bridge static source analysis (SAST) and live web transport auditing (DAST) into a unified developer workflow. It enforces security checks aligned with the OWASP Top 10 (2021) standard, featuring line-by-line regex matching, Python AST inspection, requirements manifest auditing, and baseline-aware HTTP/TLS dynamic probing. This evaluation provides an in-depth breakdown across three core dimensions: the academic and industrial Research Gaps separating this prototype from modern state-of-the-art tools, the internal System Architecture and data pipelines, and the current Implementation Progress across each OWASP vulnerability category.

1. Research Gap Analysis

While owaspscan achieves high speed and independence from external packages, it currently operates on syntactic heuristics rather than semantic flow formalisms. Bridging the gap to enterprise-grade security analysis requires addressing several theoretical and architectural limitations.

1.1 Static Analysis (SAST) Formalisms & Gaps

  • Source-to-Sink Taint & Dataflow Tracking: The scanner relies on single-line regular expressions (e.g. open(...request.args...)). In real applications, untrusted user input (sources) propagates across variables, helper utilities, and object properties before reaching dangerous operations (sinks). The lack of taint analysis causes both false negatives (missed multi-line flows) and false positives (flagging sanitized inputs).
  • Call Graph & Control Flow Graph (CFG) Construction: The AST inspector currently performs shallow walks on function decorators and bodies looking for keyword strings (e.g. login_required, current_user). It lacks an interprocedural call graph, alias analysis, or Static Single Assignment (SSA) intermediate representation. It cannot recognize framework-level middleware, blueprint auth guards, or dependency-injected security dependencies (such as FastAPI Depends).
  • Polyglot Syntax Tree Parsing: While regex rules support multi-language file extensions (.js, .ts, .php, .java, .go, .rb), AST parsing is restricted exclusively to Python via the standard ast library. Non-Python languages receive no semantic structure validation. Adopting Tree-sitter or concrete syntax trees (CST) is necessary for true polyglot analysis.
  • Software Composition Analysis (SCA) & Advisory Feeds: The manifest scanner merely flags unpinned dependency versions (missing ==). It lacks dependency tree resolution, transitive dependency graph traversal, lockfile parsing (Pipfile.lock, poetry.lock), and queries against vulnerability advisories (OSV, CVE, NVD, or PyPI Advisory Database via pip-audit).
  • OWASP A04 Insecure Design & Threat Modeling Formalisms: A04 flaws (e.g. lack of rate limiting, insecure credential recovery, business logic flaws) cannot be detected by pattern matching. Emerging research relies on automated STRIDE threat modeling, formal specifications, and LLM-assisted design reasoning to uncover architectural security weaknesses.

1.2 Dynamic Analysis (DAST) Formalisms & Gaps

  • Automated Crawling & Attack Surface Mapping: webscan audits only explicitly provided URLs and query parameters. It lacks a dynamic spider or headless browser (such as Playwright/Chromium) to explore client-rendered Single Page Applications (SPAs), discover hidden links, or trigger DOM events and form submissions.
  • Session State & Multi-Role Authentication Testing: The dynamic scanner operates purely unauthenticated. It cannot maintain stateful sessions, handle CSRF tokens, or perform privilege escalation testing (BOLA / IDOR) across multi-tenant authorization boundaries.
  • Advanced Injection Oracles & Exploit Verification: The SQLi probe relies exclusively on error-based pattern matching triggered by single quotes. It cannot detect Blind SQLi (time-based SLEEP or boolean differential queries) or Second-Order SQLi. Similarly, XSS checking is limited to verbatim reflection of GET parameters, missing DOM-based XSS, context-sensitive escaping, and POST payloads.
  • Protocol & Cipher Suite Depth: Currently limited to HTTP/1.1 via http.client and basic TLS handshake metadata. It lacks deeper auditing for HTTP/2, HTTP/3, WebSocket vulnerabilities, or fine-grained TLS cipher suite negotiation weaknesses.

2. System Architecture

owaspscan follows a modular, decoupled architecture centered around clean separation of data models, rule declarations, execution engines, and reporting adapters.

2.1 Core Modules & Responsibilities

  • cli.py (Entry Point): Manages argument parsing using argparse, subcommand dispatch (scan, web, rules), severity filtering, and CI failure threshold gating (--fail-on).
  • models.py (Data Domain): Defines Severity IntEnum (LOW, MEDIUM, HIGH, CRITICAL), the Finding normalized dataclass, and the OWASP Top 10:2021 mapping dictionary.
  • scanner.py (Static Engine): Implements recursive file discovery (iter_files) with directory pruning (.git, node_modules, venvs, tests) and file size bounds (MAX_BYTES = 1MB). Orchestrates regex scanning, AST scanning, and requirements manifest parsing.
  • rules/ (Rule Catalog): Separates rule definitions from traversal logic. regex_rules.py defines 14 compiled RegexRule frozen dataclasses. ast_rules.py implements Python AST visitors for route IDOR detection (OWS-A01-002) and swallowed exceptions (OWS-A09-002).
  • webscan.py (Dynamic Engine): Performs HTTP(S) network requests via http.client following up to 6 redirects. Gathers TLS certificates and versions. Runs passive audits (headers, cookies, transport) and active probes (soft-404 baseline diffing and injection reflection).
  • reporters.py (Presentation Layer): Outputs formatted terminal text with severity tags and remediation guidance, or structured JSON for CI/CD pipeline integration.

2.2 Static Analysis Pipeline Flow

  1. Ingestion: scan_paths() accepts CLI path arguments and invokes iter_files().
  2. Pruning: Directories matching SKIP_DIRS (.git, node_modules, venv, tests) and files > 1 MB are ignored.
  3. Multi-path Analysis:
    • Manifest Audit: requirements*.txt files are scanned for unpinned packages.
    • Regex Inspection: Lines are matched against extension-filtered RegexRules. Comments and lines tagged with # noscan are skipped.
    • AST Parsing: .py files are parsed into an AST and analyzed with AST_CHECKS.
  4. Consolidation: Findings are deduplicated by (rule_id, path, line) and sorted in descending severity.
  5. Output & CI Gate: Results are filtered by --min-severity and formatted. If any finding exceeds --fail-on, exit code 1 is emitted.

2.3 Dynamic Analysis Pipeline Flow

  1. Permission Guard: Verifies --i-have-permission flag before sending network traffic.
  2. Fetch Chain: Connects via http.client, follows redirects up to 6 hops, inspects TLS certificate validity and TLS protocol version.
  3. Passive Auditing: Evaluates response headers for CSP, HSTS, X-Frame-Options, and version disclosure. Audits Set-Cookie headers for HttpOnly, Secure, and SameSite attributes.
  4. Soft-404 Baseline Probing: Requests a random nonexistent endpoint to establish baseline response size and status code, preventing false positives on catch-all servers.
  5. Sensitive Path Discovery: Sequentially tests 13 critical endpoints (.git/HEAD, .env, .htpasswd) paced by --delay.
  6. Parameter Probing: Injects unique test tokens into GET query parameters to test unescaped HTML reflection (XSS) and database error triggers (SQLi).
